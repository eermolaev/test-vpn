# ТЗ. Разделы 3–8. Скрытность соединения и страна выхода

> Фрагмент технического задания на VPN-клиент для macOS (AmneziaWG + VLESS/REALITY).
> Нумерация разделов сохранена из исходного документа.

**Принятые решения (рамки проекта)**

| Тема | Решение |
| --- | --- |
| Назначение | Личное использование, без публичной дистрибуции |
| macOS | Начиная с macOS 26 |
| AmneziaWG | Последняя стабильная версия протокола (см. 4.2) |
| Движки | Два: xray-core (VLESS + REALITY) и amneziawg-go (AmneziaWG) |
| IPv6 на серверах | Нет; IPv6 на клиенте всегда блокируется (GEO-003) |
| Топология сервера | Один узел: вход и выход на одном сервере (разнесение — опция на будущее, 3.3) |
| DNS | Публичный резолвер, по умолчанию Google `8.8.8.8` / `8.8.4.4`; адреса настраиваются (GEO-010) |
| Проверки IP | Публичные сервисы определения IP; собственная инфраструктура для проверок не разворачивается |

**Обозначения приоритета**

- **ОБЯЗ.** — обязательно для релиза.
- **ЖЕЛ.** — желательно; допускается перенос в следующую версию с фиксацией в backlog.
- **ОПЦ.** — опционально, включается пользователем явно.

Каждое требование содержит: формулировку, критерий приёмки (КП) и способ проверки (Пров.).

## 3. Модель угроз и два независимых требования к скрытности

### 3.1. Активы

| Актив | Почему важен |
| --- | --- |
| Факт и содержимое трафика пользователя | Не должны быть видны провайдеру в открытом виде |
| Исходный IP и страна пользователя | Не должны быть видны удалённым сайтам |
| Секреты профиля (ключи, UUID, `shortId`, публичный ключ REALITY, параметры обфускации) | Компрометация позволяет выявить и заблокировать сервер или выдать себя за клиента |
| Адрес VPN-сервера | Раскрытие упрощает блокировку по IP |

### 3.2. Противники и их возможности

| Противник | Возможности | Что от него защищает |
| --- | --- | --- |
| Провайдер / DPI-оборудование | Сигнатурный анализ пакетов, анализ TLS ClientHello (SNI, fingerprint), проверка соответствия SNI и IP/ASN, ограничение или блокировка UDP, блокировка по IP и подсетям, замедление | Уровень A |
| Активный зондировщик | Подключается к IP сервера сам и проверяет его реакцию | Серверная настройка REALITY / AmneziaWG (вне клиента, но клиент должен быть совместим) |
| Статистический анализ | Объём, длительность, размеры и тайминги пакетов, долгоживущие соединения с высоким трафиком | Частично: Vision, параметры AmneziaWG. Полной защиты нет |
| Удалённый сайт | GeoIP, репутация IP, ASN хостинга, списки VPN-диапазонов, WebRTC, часовой пояс, язык, Geolocation API браузера, данные аккаунта | Уровень B (только сетевая часть) |

### 3.3. Уровни скрытности

Уровни A и B решаются разными механизмами и не гарантируют друг друга. В ТЗ, тестах и интерфейсе они учитываются раздельно.

**Уровень A — провайдер между Mac и VPN-сервером.**
Цель: затруднить распознавание протокола и блокировку по сигнатуре, уменьшить число явных признаков VPN.
Средства: AmneziaWG, VLESS + REALITY, выбор транспорта, резервные подключения, классификация сетевых ошибок.

**Уровень B — сайты и сервисы, к которым подключается пользователь.**
Цель: сайты должны видеть фактический IP выхода VPN-сервера, а не исходный IP Mac.
Средства: полная маршрутизация, отсутствие утечек (DNS, IPv6, WebRTC, обход маршрута), проверка внешнего IP и его геолокации.

**Опция архитектуры сервера на будущее — разнесение входа и выхода (bridge → exit).** Не используется в текущей версии: вход и выход на одном сервере.
Схема: Mac подключается к серверу №1 (вход), а тот пересылает трафик на сервер №2 (выход), откуда он уходит в интернет. Если входной узел (его IP видит провайдер) и выходной узел (его IP видят сайты) разные, уровни развязываются: блокировка входного IP не портит репутацию выходного, а выходной IP не появляется в трафике провайдера. Это серверная настройка; клиент должен показывать в диагностике оба адреса как разные сущности («сервер подключения» и «IP выхода»).

### 3.4. Ограничения (non-goals)

- Нельзя гарантировать, что VPN-трафик не будет обнаружен. Даже если транспорт похож на обычный HTTPS, провайдер может заблокировать IP сервера или применить статистический анализ.
- Удалённый сайт может отнести выходной IP к VPN/хостингу независимо от качества маскировки между Mac и сервером.
- Клиент не исправляет записи в чужих GeoIP-базах.
- Клиент не маскирует признаки уровня браузера и ОС (часовой пояс, язык, отпечаток браузера, данные аккаунта, Geolocation API). Он только предупреждает о них (см. GEO-009).
- Клиент не реализует собственную криптографию или обфускацию поверх штатных механизмов протоколов.

## 4. Уровень A: усложнение обнаружения и блокировки

### 4.1. Транспорты и политика их использования

| Режим | Политика | Применение | Ограничения |
| --- | --- | --- | --- |
| AmneziaWG (версия протокола — см. 4.2) | Основной | Обфусцированный WireGuard: мусорные пакеты, сдвиги заголовков, нестандартные типы сообщений | Только UDP; бесполезен, если UDP заблокирован или сильно ограничен |
| VLESS + REALITY, RAW/TCP + `xtls-rprx-vision` | Основной / резерв при проблемах с UDP | TLS 1.3 с имитацией реального сайта; Vision устраняет характерный признак TLS-in-TLS | Зависит от выбора `dest`/SNI на сервере и совместимости версий движка |
| VLESS + REALITY, XHTTP | Резерв | Когда прямое долгоживущее TCP-соединение режется или замедляется | Выше задержки; требует поддержки на сервере |
| Обычный WireGuard | Только вручную | Максимальная скорость в сетях без DPI | Легко распознаётся; **никогда не выбирается автоматически** |
| VLESS без TLS/REALITY | Запрещён в UI для внешних сетей | Отладка, локальные стенды | Не защищает от DPI; трафик VLESS виден в открытом виде |

### 4.2. Параметры протоколов

**AmneziaWG.** Используется последняя стабильная версия протокола на момент начала разработки. На момент написания это AmneziaWG 2.0: параметры `Jc`, `Jmin`, `Jmax`, `S1…S4`, диапазоны `H1…H4`, сигнатурные пакеты `I1…I5`. Перед стартом версию нужно сверить с docs.amnezia.org и репозиторием amneziawg-go. Название «AmneziaWG 3.1» из исходной версии ТЗ, по-видимому, относится к версии клиента Amnezia VPN, а не протокола.
Требования:
- версия протокола и коммит amneziawg-go фиксируются в манифесте сборки (SEC-NET-006), отдельно от версии приложения;
- клиент принимает конфигурации с полным набором параметров последней версии и отклоняет неизвестные параметры с понятной ошибкой, не игнорируя их молча;
- сервер обновляется до той же версии протокола; несовпадение версий диагностируется как отдельная ошибка (SEC-NET-004).

**VLESS + REALITY.** Клиент поддерживает параметры профиля: `publicKey`, `shortId`, `serverName` (SNI), `fingerprint` (uTLS, по умолчанию `chrome`), `flow` (`xtls-rprx-vision` для RAW/TCP), `spiderX`, тип транспорта. Требования к серверу, влияющие на скрытность (вне клиента, но фиксируются в документации для администратора):

- `dest`/SNI — реальный сайт с TLS 1.3 и HTTP/2, по возможности в той же сети или стране, что и сервер. Резкое несоответствие SNI и ASN сервера (например, SNI крупного зарубежного сервиса на IP мелкого хостинга) — известный признак для DPI.
- Сервер должен корректно отвечать посторонним клиентам содержимым `dest` (защита от активного зондирования).

**UDP в режиме VLESS.** UDP-трафик приложений либо передаётся через XUDP поверх туннеля, либо блокируется. Прямой выход UDP недопустим. QUIC (UDP 443) по умолчанию блокируется, чтобы браузеры переходили на TCP: QUIC поверх TCP-туннеля работает хуже. Поведение настраивается.

### 4.3. Требования

**SEC-NET-001. Несколько способов подключения в профиле.** ОБЯЗ.
Профиль может содержать несколько совместимых транспортов с порядком предпочтения. Переключение между ними не меняет и не пересылает секреты, выданные сервером.
КП: профиль с AmneziaWG и двумя вариантами REALITY импортируется, каждый транспорт подключается отдельно.
Пров.: интеграционный тест на стенде.

**SEC-NET-002. Подтверждение отказа перед переключением.** ОБЯЗ.
Переход на другой транспорт выполняется только после подтверждённого отказа текущего: нет handshake / нет ответа на проверочный запрос через туннель в течение `T_fail` (по умолчанию 10 с, настраивается) после `N` попыток (по умолчанию 3). Между попытками — экспоненциальная задержка с ограничением. Общее число циклов переключения ограничено (по умолчанию 3 полных круга), затем — состояние «Нет соединения» с объяснением, без бесконечных переподключений.
КП: при блокировке UDP на стенде переключение на REALITY занимает не более `N × T_fail + 5 с`; при блокировке всех транспортов клиент останавливается после лимита.
Пров.: стенд с управляемым фильтром (pf/nftables).

**SEC-NET-003. Резерв при блокировке UDP.** ОБЯЗ.
При недоступности UDP и наличии в профиле REALITY клиент переходит на VLESS + REALITY (RAW/TCP + Vision, затем XHTTP).
**Запрещено** автоматически переходить на транспорт с более слабой защитой от DPI (обычный WireGuard, VLESS без REALITY/TLS).
КП: автоматический переход на транспорт с политикой «Только вручную» или «Запрещён» невозможен ни при каком сценарии отказа.
Пров.: юнит-тесты `ConnectionFallbackPolicy` и интеграционный тест.

**SEC-NET-004. Классификация ошибок.** ОБЯЗ.
Различаются и отдельно показываются в диагностике:

| Класс | Признаки |
| --- | --- |
| DNS | Не разрешилось имя сервера (если оно задано доменом) |
| Нет сети | Нет маршрута по умолчанию, captive portal |
| Тайм-аут UDP | Нет ответа на handshake AmneziaWG |
| TCP сброшен / тайм-аут | RST, отсутствие SYN-ACK |
| Ошибка TLS/REALITY | Ошибка handshake, неверный ключ, несоответствие `shortId` |
| Несовместимость AmneziaWG | Сервер отвечает, но параметры обфускации или версия протокола не совпадают |
| Ошибка маршрутизации | Туннель поднят, но проверочный запрос через него не проходит |

Тайм-аут сам по себе не считается доказательством блокировки; UI не пишет «VPN заблокирован» без достаточных признаков.
КП: каждый класс воспроизводится на стенде и даёт отдельный код ошибки.
Пров.: интеграционные тесты с инъекцией отказов.

**SEC-NET-005. Запоминание рабочего транспорта для сети.** ЖЕЛ.
Последний успешный транспорт запоминается для идентификатора сети (хэш SSID/шлюза, без хранения открытых значений) и при следующем подключении пробуется первым. Это сокращает число неудачных попыток: частая смена протоколов сама по себе заметна.
КП: повторное подключение в той же сети начинается с последнего успешного транспорта.
Пров.: юнит-тест.

**SEC-NET-006. Обновляемые движки с фиксированными версиями.** ОБЯЗ.
Используются два движка: xray-core для VLESS + REALITY и amneziawg-go для AmneziaWG. Одновременно активен только один из них. Их версии фиксируются в манифесте сборки, обновляются только после прохождения матрицы совместимости (раздел 8.4). Собственные варианты криптографической маскировки не реализуются.
КП: версия каждого движка видна в «О программе» и в диагностическом отчёте.
Пров.: проверка сборки в CI.

**SEC-KILL-001. Строгая маршрутизация (kill switch).** ОБЯЗ.
*Объединяет SEC-NET-005 и GEO-004 исходной версии.*
В режиме полного туннеля перехваченный трафик ни при каких условиях не уходит напрямую через физический интерфейс, в том числе:

- при запуске до установления туннеля;
- при переподключении и смене транспорта;
- при сне и пробуждении Mac, при смене сети (Wi-Fi ↔ Ethernet ↔ точка доступа);
- при падении или перезапуске Network Extension либо движка;
- во время обновления приложения.

Исключения: трафик самого движка к серверу VPN; локальная сеть (только при явно включённой настройке); captive portal (только через явное действие пользователя с предупреждением). Все исключения документируются и видны в UI.
КП: при захвате трафика на физическом интерфейсе (`tcpdump -i en0`) во всех перечисленных сценариях нет ни одного пакета, кроме трафика к IP сервера VPN и разрешённых исключений.
Пров.: автоматизированный сценарий с pcap и скриптом-анализатором (раздел 8.4).

**SEC-LOG-001. Секреты не попадают в логи и отчёты.** ОБЯЗ.
Ключи, UUID, `shortId`, параметры обфускации и полный адрес сервера маскируются в логах и диагностическом отчёте. Секреты хранятся в Keychain (общая access group приложения и extension).
КП: поиск значений секретов тестового профиля в логах и отчёте даёт 0 совпадений.
Пров.: автоматический тест.

## 5. Уровень B: правильная страна для удалённых систем

### 5.1. Как сайт определяет страну

Сайт видит публичный IP выхода VPN-сервера и определяет страну по своей GeoIP-базе. Дополнительно он может учитывать принадлежность IP хостингу (ASN), репутацию адреса, известные VPN-диапазоны, а также сигналы, не связанные с сетью: часовой пояс и язык системы, Geolocation API браузера (на macOS — Core Location по окружающим Wi-Fi сетям), данные аккаунта.

Пример: сервер физически находится в Германии, но GeoIP-базы относят его IP к Нидерландам — сайт определит Нидерланды. Клиент не может это исправить. Разные поставщики GeoIP могут расходиться, стопроцентная точность не гарантируется [3].

### 5.2. Конвейер проверки выхода

```
1. Туннель поднят        → профиль, ожидаемая страна
2. Публичные адреса      → IPv4 и IPv6 выхода, ≥2 независимых источника, консенсус
3. Геолокация            → страна по локальной GeoIP-базе (+ опционально внешние сервисы)
4. Проверка утечек       → DNS, IPv6, WebRTC/STUN, обход маршрута, UDP
5. Результат             → фактическая страна, совпадение с ожидаемой, предупреждения
```

Проверка запускается после подключения, после смены сети, после восстановления соединения и после смены транспорта, а также по запросу пользователя.

### 5.3. Требования

**GEO-001. Фактическая страна выхода.** ОБЯЗ.
Страна определяется по публичному IP выхода, а не по названию профиля, домену сервера или заявленной локации.
КП: при профиле «Германия» и выходном IP, который GeoIP относит к Франции, отображается «Франция» и предупреждение о несоответствии.
Пров.: тест с подменой ответа GeoIP-провайдера.

**GEO-002. Консенсус источников IP.** ОБЯЗ.
Внешний IP определяется по публичным сервисам: минимум два независимых из настраиваемого списка, например `https://api.ipify.org`, `https://icanhazip.com`, `https://ifconfig.co`, `https://www.cloudflare.com/cdn-cgi/trace`. Сервисы опрашиваются в случайном порядке, у каждого свой тайм-аут; недоступность одного сервиса не считается ошибкой VPN. При расхождении ответов показывается предупреждение. Запросы идут только через туннель, по HTTPS, без cookies и идентификаторов. Сервисы видят только IP выхода; секреты профиля и адрес сервера им не передаются.
КП: при расхождении источников результат помечается «не подтверждён».
Пров.: юнит-тест `ExitIPResolver` с моками.

**GEO-003. IPv4 и IPv6.** ОБЯЗ.
На серверах нет IPv6, поэтому весь IPv6 (`::/0`) направляется в туннель и отбрасывается внутри extension. Прямой выход IPv6 недопустим. AAAA-ответы DNS не фильтруются: приложения получают ошибку IPv6-соединения и переходят на IPv4 (Happy Eyeballs). В диагностике IPv6 показывается как «заблокирован (сервер без IPv6)», а не как ошибка.
Работа в IPv6-only сетях с NAT64 не гарантируется: подключение к IPv4-адресу сервера через NAT64 проверяется как ЖЕЛ.
КП: на машине с нативным IPv6 запрос `curl -6 https://api64.ipify.org` не проходит, а pcap на физическом интерфейсе не содержит IPv6-пакетов, кроме link-local и служебных ICMPv6.
Пров.: сеть с dual-stack (например, мобильная точка доступа с IPv6).

**GEO-004. DNS.** ОБЯЗ.
Используется публичный резолвер: по умолчанию Google Public DNS `8.8.8.8` / `8.8.4.4`, адреса настраиваются (GEO-010). Системный DNS указывается в настройках туннеля, все DNS-запросы (UDP/TCP 53, DoT 853) идут через туннель. Поэтому резолвер видит IP выхода, а anycast направляет запросы на узел рядом с сервером. Google передаёт авторитетным серверам EDNS Client Subnet, и это будет подсеть IP выхода, а не провайдера пользователя. В итоге CDN с geo-DNS отдают ресурсы региона выхода. DNS-провайдер пользователя (из DHCP) не используется. Браузерный DoH допускается, поскольку идёт через туннель.
Проверяется фактический путь запросов, а не только настроенный адрес:
1. pcap на физическом интерфейсе не содержит DNS-трафика (порты 53/853) — основной критерий, своя инфраструктура не нужна;
2. дополнительно — публичный DNS leak test (например, browserleaks.com/dns или dnsleaktest.com), вручную или через API, если сервис его предоставляет: резолверы в результате должны принадлежать выбранному публичному DNS, а не провайдеру.
КП: в pcap на физическом интерфейсе 0 DNS-пакетов; leak test показывает только резолверы выбранного публичного DNS.
Пров.: автоматизированный pcap-сценарий + ручной leak test перед релизом.

**GEO-005. WebRTC и UDP.** ОБЯЗ.
STUN-запрос к публичному STUN-серверу (например, `stun.l.google.com:19302`, `stun.cloudflare.com:3478`) возвращает IP выхода, а не исходный IP. В режиме VLESS без XUDP UDP блокируется (см. 4.2).
КП: STUN-проверка в EgressVerifier возвращает IP выхода или ошибку, но не исходный IP.
Пров.: интеграционный тест.

**GEO-006. Активная проверка обхода.** ОБЯЗ.
EgressVerifier пытается отправить запрос к публичному сервису определения IP в обход туннеля (привязка сокета к физическому интерфейсу). В строгом режиме попытка должна завершиться ошибкой; успех — критическое предупреждение «обнаружен прямой выход».
КП: при искусственно отключённом kill switch проверка выявляет утечку.
Пров.: интеграционный тест.

**GEO-007. Отображение результата.** ОБЯЗ.
Отдельно показываются:

- ожидаемая страна профиля;
- страна фактического IPv4 и IPv6 выхода;
- сервер подключения и IP выхода (если различаются — см. 3.3);
- результат проверки маршрутизации и найденные утечки;
- источник и дата обновления GeoIP-данных.

Если ожидаемая и фактическая страны не совпадают, приложение показывает несоответствие и не заявляет, что пользователь вышел через ожидаемую страну.
КП: макеты UI утверждены, все поля заполняются на стенде.
Пров.: UI-тест.

**GEO-008. Диагностический характер проверки.** ОБЯЗ.
В UI явно указано, что проверка диагностическая: сайт может использовать другую базу и определить другую страну. Проверка опирается на локальную GeoIP-базу с регулярным обновлением; проверка через внешние сервисы — опция, выключенная по умолчанию. Учитываются лицензии баз: MaxMind GeoLite2 — EULA с регистрацией, DB-IP Lite — CC BY 4.0 (нужна атрибуция) [4].
КП: база обновляется не реже раза в месяц; дата обновления отображается.
Пров.: проверка сборки и UI.

**GEO-009. Предупреждения о несетевых сигналах.** ЖЕЛ.
Если часовой пояс системы не соответствует стране выхода, а также если включён iCloud Private Relay (конфликтует с маршрутизацией Safari) или службы геолокации, приложение показывает информационное предупреждение. Изменять настройки системы автоматически запрещено.
КП: при часовом поясе Europe/Moscow и выходе в Германии отображается предупреждение.
Пров.: юнит-тест.

**GEO-010. Настройка DNS-резолвера.** ОБЯЗ.
- По умолчанию используется Google Public DNS: `8.8.8.8` (основной) и `8.8.4.4` (резервный).
- В настройках есть выбор из пресетов: Google (по умолчанию), Cloudflare (`1.1.1.1` / `1.0.0.1`), Quad9 (`9.9.9.9` / `149.112.112.112`), «Свои адреса».
- Режим «Свои адреса»: от 1 до 4 адресов IPv4. Адреса проверяются при вводе; IPv6 не принимается, так как IPv6 заблокирован (GEO-003). Пустой список или неверный адрес сохранить нельзя.
- Глобальная настройка действует для всех профилей. В профиле можно переопределить её своим значением; профиль без переопределения использует глобальную.
- При изменении настройки во время подключения сетевые параметры туннеля применяются заново, без полного переподключения, если это возможно; иначе туннель переподключается, и kill switch действует всё это время (SEC-KILL-001).
- Резолвер, указанный в профиле от сервера, не заменяет выбор пользователя молча: если они различаются, в настройках показывается, какой реально используется.
- Выбранный резолвер отображается в диагностике (GEO-007) и в отчёте; DNS leak test (GEO-004) сверяет результат именно с ним.
КП: после смены пресета на Cloudflare `scutil --dns` показывает `1.1.1.1` для туннеля, а pcap на физическом интерфейсе по-прежнему содержит 0 DNS-пакетов; возврат к значениям по умолчанию даёт `8.8.8.8` / `8.8.4.4`.
Пров.: юнит-тест валидации + интеграционный тест смены резолвера на подключённом туннеле.

## 6. Системная маршрутизация в macOS

### 6.1. Ограничения

Локальный SOCKS5/HTTP-прокси и системные proxy-настройки не гарантируют, что весь трафик идёт через VPN: многие приложения и UDP их игнорируют. Нужен системный сетевой backend на Network Extension.

Ограничения `NETransparentProxyProvider` [5]:

- если обработчик потока возвращает `false`, соединение продолжается напрямую — это противоречит SEC-KILL-001, если не обрабатывать все потоки;
- DNS- и proxy-настройки в `NETransparentProxyNetworkSettings` этим механизмом игнорируются — DNS нужно перехватывать отдельно.

### 6.2. Варианты backend'а

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| `NEPacketTunnelProvider` (utun, полный туннель) + `includeAllNetworks` / `enforceRoutes` / `excludeLocalNetworks`; AmneziaWG — напрямую, VLESS — через мост tun → движок (tun2socks или TUN-вход движка) | Весь IP-трафик, включая UDP и DNS, попадает в туннель; системный kill switch | Мост добавляет задержку и сложность; нужно проверить совместимость `includeAllNetworks` с системными службами Apple |
| `NETransparentProxyProvider` для VLESS | Работа на уровне потоков, без собственного TCP/IP-стека | Риски из 6.1; отдельная обработка DNS и UDP; kill switch реализуется самостоятельно |

**Рекомендация:** базовый вариант — `NEPacketTunnelProvider` для обоих протоколов. Окончательный выбор для VLESS фиксируется в ADR после PoC по критериям:

1. 0 пакетов мимо туннеля по SEC-KILL-001 во всех сценариях;
2. DNS, IPv6 и UDP соответствуют GEO-003…GEO-005;
3. пропускная способность ≥ 80 % от прямого подключения к тому же серверу;
4. время восстановления после смены сети ≤ 5 с;
5. стабильная работа 24 ч без утечек памяти в extension.

**Решение по движкам:** два движка — amneziawg-go и xray-core, оба встраиваются в один packet tunnel extension как Go-библиотеки. Одновременно работает только один. Переключение транспорта полностью останавливает один движок перед запуском другого, а kill switch действует всё это время (SEC-KILL-001). Для xray-core в PoC выбирается мост: TUN-вход самого xray-core (если его возможности достаточны) или внешний tun2socks.

### 6.3. Дистрибуция и безопасность

- **Только личное использование.** Публичная дистрибуция, App Store и нотаризация не требуются. Сборка через Xcode с development-подписью и provisioning profile, где Mac зарегистрирован как устройство. Тип расширения — packet tunnel **app extension** внутри приложения: оно проще System Extension и не требует его активации. Если development-подпись окажется недостаточной, запасной вариант — System Extension с подписью Developer ID.
- Entitlement Network Extension (`packet-tunnel-provider`) требует платного членства в Apple Developer Program: бесплатная Personal Team его не выдаёт. Development-профили периодически истекают; порядок перевыпуска описывается в README.
- **Минимальная версия — macOS 26.** Можно использовать актуальные API Network Extension без проверок `#available` для старых версий. Тесты — на macOS 26 и следующих версиях по мере выхода, на архитектуре своего Mac.
- Секреты — в Keychain с общей access group приложения и extension; в файлы и `UserDefaults` не пишутся.

## 7. Можно ли скрыть от сайтов сам факт VPN

Не гарантированно. REALITY и AmneziaWG действуют только между Mac и VPN-сервером. Сайт видит соединение с IP выхода и не видит, каким транспортом пользователь до него добрался. Но он может распознать VPN по диапазонам адресов, ASN, репутации IP и несетевым сигналам.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Выходной IP геолоцируется в нужной стране | Сайт обычно определяет эту страну |
| IP в нужной стране, но принадлежит хостингу или известен как VPN | Страна определяется правильно, VPN/прокси может обнаруживаться отдельно |
| IPv6, DNS или WebRTC выходят напрямую | Сайт может увидеть исходную страну или IP |
| Резолвер DNS в другой стране, чем выход | CDN может отдавать контент другого региона |
| GeoIP-база сайта устарела или расходится с остальными | Сайт определяет другую страну |
| Часовой пояс, язык или Geolocation API не соответствуют стране выхода | Сайт может заподозрить VPN или определить реальное местоположение |
| Сайт использует данные аккаунта или устройства | Страна по IP не гарантирует совпадения всех сигналов |

Рекомендации для выбора сервера (документация для пользователя и администратора): выходной IP должен одинаково геолоцироваться в нескольких базах (MaxMind, IP2Location, ipinfo, DB-IP); для критичных сценариев учитывать тип ASN (хостинг или резидентный). Если сам факт VPN недопустим для конкретного сайта, результат зависит от политики сайта, и клиент не может его гарантировать.

## 8. Модули, этапы, тестирование

### 8.1. Модули

```
Security/
├── ConnectionFallbackPolicy.swift   # SEC-NET-002/003/005: порядок, лимиты, запрет понижения защиты
├── StrictRoutingPolicy.swift        # SEC-KILL-001: правила и исключения
├── TrafficLeakMonitor.swift         # фоновые признаки утечек
├── SecretRedactor.swift             # SEC-LOG-001
└── EgressVerifier.swift             # оркестрация конвейера 5.2

Network/
├── ExitIPResolver.swift             # GEO-002: несколько источников, консенсус
├── GeoIPProvider.swift              # GEO-008: локальная база + опциональные внешние
├── DNSRouteVerifier.swift           # GEO-004
├── DNSSettings.swift                # GEO-010: пресеты, свои адреса, валидация
├── IPv6RouteVerifier.swift          # GEO-003
├── WebRTCLeakVerifier.swift         # GEO-005
├── BypassProbe.swift                # GEO-006
├── ErrorClassifier.swift            # SEC-NET-004
└── RoutingHealthCheck.swift         # проверочные запросы через туннель

Diagnostics/
└── DiagnosticReport.swift           # версии движков, коды ошибок, результаты проверок (без секретов)
```

`EgressVerifier` не раскрывает секреты профиля сторонним сервисам и не блокирует UI: проверка выполняется асинхронно, результат кэшируется до следующего события сети.

### 8.2. Этапы реализации

| Этап | Содержание | Критерий готовности |
| --- | --- | --- |
| 0. PoC backend'а | `NEPacketTunnelProvider` + встраивание движков, мост для VLESS, канал дистрибуции | ADR по критериям 6.2 |
| 1. Строгая маршрутизация | SEC-KILL-001 на одном протоколе (AmneziaWG) | pcap-тест: 0 пакетов мимо туннеля во всех сценариях |
| 2. Второй протокол | VLESS + REALITY (Vision, затем XHTTP) в том же backend'е | SEC-KILL-001 и GEO-003…005 проходят для REALITY |
| 3. Проверка выхода | EgressVerifier, GEO-001…008, GEO-010 | Все GEO-требования ОБЯЗ. проходят на стенде |
| 4. Резервирование | SEC-NET-001…005, классификация ошибок | Сценарии отказа из 8.4 проходят без нарушения SEC-KILL-001 |
| 5. Диагностика и UX | GEO-007, GEO-009, диагностический отчёт | Утверждённые макеты, SEC-LOG-001 |

Тесты пишутся на каждом этапе вместе с функциональностью, а не отдельным этапом.

### 8.3. Метрики

| Метрика | Целевое значение |
| --- | --- |
| Пакеты мимо туннеля (pcap, все сценарии SEC-KILL-001) | 0 |
| Время подключения на основном транспорте | ≤ 3 с (медиана) |
| Время перехода на резерв при блокировке UDP | ≤ `N × T_fail + 5 с` |
| Восстановление после смены сети или пробуждения | ≤ 5 с |
| Пропускная способность относительно прямого подключения к серверу | ≥ 80 % |
| Ложные сообщения «VPN заблокирован» при простом тайм-ауте | 0 |

### 8.4. Матрица тестов

- **Сети:** Wi-Fi, Ethernet, точка доступа телефона, captive portal, dual-stack; IPv6-only + NAT64 — ЖЕЛ.
- **Фильтрация на стенде:** блокировка UDP, блокировка UDP 443, блокировка IP сервера, RST на TCP, замедление, подмена DNS.
- **События:** сон/пробуждение, смена сети, падение extension (`kill -9`), обновление приложения, смена транспорта.
- **Проверки:** pcap на физическом интерфейсе, DNS leak (уникальный поддомен), IPv6 leak, WebRTC/STUN, обход туннеля (GEO-006), отсутствие секретов в логах.
- **Версии:** macOS 26 и новее; архитектура своего Mac; фиксированные версии движков, версии протокола AmneziaWG и серверов.
